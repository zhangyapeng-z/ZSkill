# 回退与恢复策略

## 总体策略

每个阶段在开始前创建 Git checkpoint（通过 `git commit`），
失败时回退到该 checkpoint，必要时回退到更早的阶段。

```
checkpoint-0: 拆分前基线
    │
checkpoint-1: 分析完成
    │
checkpoint-2: 规划完成
    │
checkpoint-3-N: 执行步骤 N 完成（每步一个 checkpoint）
    │
checkpoint-4: 检查完成
    │
checkpoint-5: 验证完成
```

---

## 各阶段回退详情

### 阶段一：分析阶段回退

| 失败场景 | 回退方式 | 重试策略 |
|----------|----------|----------|
| 目录扫描不完整（超大项目超时） | 无需回退，调整参数重试 | 增加文件数限制，分批扫描 |
| `mvn dependency:tree` 执行失败 | 回退到纯 POM 解析模式 | 降级方案：只解析 pom.xml 文本 |
| 依赖图构建异常（JSON 格式错误） | 重新构建，不丢已有数据 | 修复解析逻辑后重试 |
| 业务边界识别不足 | 请求用户提供业务域提示 | 带提示重跑识别阶段 |

**回退目标**：checkpoint-0（拆分前基线），清理 `analysis/` 目录后重跑。

**重试上限**：3 次。超过则标记 `Failed`，输出已收集的部分分析数据。

---

### 阶段二：规划阶段回退

| 失败场景 | 回退方式 | 重试策略 |
|----------|----------|----------|
| 存在无法消除的循环依赖 | 回退到分析阶段，补充分析 | 聚焦循环依赖涉及的包，深度分析 |
| 模块边界模糊（职责重叠>30%） | 回退到分析阶段 | 请求用户给出业务域拆分意见 |
| common 模块过大（>50 类） | 在当前阶段调整 | 自动拆分为 common-dto/util/config 子模块 |
| 用户否决拆分方案 | 回退到分析阶段 | 根据用户反馈调整分析焦点 |

**回退目标**：checkpoint-1（分析完成后），清理 `plan/` 目录后重新规划。

**重试上限**：3 次。超过则请求 Orchestrator 人工介入。

---

### 阶段三：执行阶段回退

这是最复杂的回退场景，因为执行阶段修改了实际工程文件。

| 失败场景 | 回退方式 | 重试策略 |
|----------|----------|----------|
| 单模块迁移失败（编译错误） | `git reset --hard checkpoint-3-(N-1)` | 修复问题后重试当前步骤 |
| 多个模块迁移后发现架构问题 | `git reset --hard checkpoint-2` | 回退到规划阶段调整方案 |
| 文件冲突（目标路径已存在） | 检查冲突文件来源，决策覆盖/跳过 | 手动解决冲突后继续 |
| Git 历史丢失 | 改用 `git mv` 命令迁移文件 | 确保使用保留历史的操作 |

**详细回退流程**：

```
Step N 执行失败
  │
  ├── 是编译错误？
  │   ├── 能立即修复（如 import 遗漏）？
  │   │   └── YES → 就地修复，重新编译，继续
  │   └── 无法立即修复？
  │       └── git reset --hard checkpoint-3-(N-1)
  │           记录失败原因到 migration-log.md
  │           通知 Orchestrator：方案需调整
  │
  ├── 是架构问题（如发现循环依赖无法解决）？
  │   └── git reset --hard checkpoint-2
  │       回退到规划阶段
  │       在 violation-list.json 中记录发现的问题
  │       重新规划（含已知约束）
  │
  └── 是文件冲突？
      └── 暂停执行
          报告冲突详情给 Orchestrator
          等待人工决策
```

**回退目标**：
- 小问题：checkpoint-3-(N-1)（上一个步骤的 checkpoint）
- 大问题：checkpoint-2（规划完成后，即回退到执行前）
- 极端情况：checkpoint-0（拆分前基线）

**重试上限**：每个步骤最多 3 次。整个执行阶段最多回退规划阶段 2 次。

---

### 阶段四：检查阶段回退

| 失败场景 | 回退方式 | 重试策略 |
|----------|----------|----------|
| CRITICAL 违规（循环依赖） | 回退到执行阶段 | 定向修复违规模块 |
| 多模块边界泄漏 | 回退到执行阶段 | 批量调整模块归属 |
| 遗漏代码（未迁移） | 回退到执行阶段 | 补充迁移遗漏文件 |

**回退目标**：checkpoint-3-N（执行阶段最后一个 checkpoint），即检查前的状态。

**具体流程**：

```
发现违规列表
  │
  ├── CRITICAL 违规 > 0
  │   └── 生成 violation-list.json
  │       回退到执行阶段
  │       Executor 读取 violation-list.json
  │       仅修复违规项（不重做全部迁移）
  │       重新检查
  │
  ├── WARNING 违规 > 2
  │   └── 评估是否可以接受
  │       ├── 可接受 → 记录到决策日志，继续
  │       └── 不可接受 → 回退执行阶段
  │
  └── 只有 INFO 违规
      └── 记录到报告，继续到验证阶段
```

**重试上限**：最多回退执行阶段 2 次。

---

### 阶段五：验证阶段回退

| 失败场景 | 回退方式 | 重试策略 |
|----------|----------|----------|
| 编译失败 | 回退到执行阶段 | 修复编译问题的模块 |
| 测试失败（新增失败） | 回退到执行阶段 | 检查测试类和依赖配置 |
| Bean 注入失败 | 回退到执行阶段 | 调整 Spring 配置和模块依赖 |
| 启动失败 | 回退到执行阶段 | 检查启动类和所有依赖 |

**回退目标**：checkpoint-4（检查完成后，即验证前的状态）。

**具体流程**：

```
验证失败
  │
  ├── 编译失败
  │   └── 输出具体错误文件列表
  │       回退到执行阶段
  │       Executor 按错误列表逐文件修复
  │       重新检查 → 重新验证
  │
  ├── 测试失败
  │   └── 输出失败测试列表 + 堆栈
  │       分析根因：
  │       ├── 迁移遗漏 → 回退执行阶段补充
  │       ├── import 错误 → 回退执行阶段修复
  │       └── 测试环境问题 → 通知 Orchestrator
  │
  └── 启动失败
      └── 输出完整启动日志
          常见原因：
          ├── @ComponentScan 未覆盖新模块 → 调整 scanBasePackages
          ├── 缺少 @Configuration 导入 → 补充 @Import
          └── 配置属性缺失 → 检查 application.yml
```

**重试上限**：最多回退执行阶段 2 次。

---

## 全局回退规则

### 重试计数

```
analysisRetries    = 0  (max: 3)
planningRetries    = 0  (max: 3)
executionRetries   = 0  (max: 3 per step, 2 per full rollback)
inspectionRetries  = 0  (max: 2 for execution rollback)
verificationRetries = 0 (max: 2 for execution rollback)
```

### 熔断条件

当出现以下任一情况时，Orchestrator 宣告整个流水线 `Failed`：

1. 同一阶段重试超过上限
2. 回退到 checkpoint-0 后仍然失败
3. 发现需要在业务逻辑层面重构的架构问题（超出模块拆分范围）
4. 用户主动终止

### 失败后的数据保留

流水线 `Failed` 后：
- 保留所有 `/shared/specs/` 中的产出文件
- 保留 `/shared/decisions/` 中的架构决策
- 保留 `migration-log.md` 作为问题分析依据
- 通过 `git reset --hard checkpoint-0` 恢复工程到拆分前状态
- 输出《失败总结报告》到 `/shared/specs/failure-report.md`
