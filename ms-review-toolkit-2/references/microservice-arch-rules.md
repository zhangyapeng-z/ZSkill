# 微服务架构检查规则

本文件定义微服务架构维度的全部检查规则（M-01 ~ M-10），每条规则包含：判定目标、命中条件、排除条件（避免误报）、严重级别、解决方案与最佳实践。

---

## M-01 服务拆分合理性

**判定目标**：服务是否按业务领域（限界上下文）拆分，粒度是否合理。

**命中条件（满足任一即疑似）**：
- 单服务 Java 文件数 > 阈值（默认 200）或代码行数 > 阈值（默认 30000）——疑似"伪微服务"（单体拆分不充分）
- 单服务 Java 文件数 < 阈值（默认 5）——疑似过度拆分（纳米服务）
- 单服务内出现多个不相关业务上下文包（如 `com.xxx.order` 与 `com.xxx.payment` 同处一个服务）——领域边界不清
- 服务名/模块名含 `service`/`biz`/`all`/`core` 等泛化词且文件数巨大——疑似"大泥球服务"

**排除条件（不报）**：
- 工程总服务数为 1 且无注册发现组件 → 非微服务工程，跳过本规则集（整组规则不触发）
- 单服务为基础设施服务（网关/配置中心/注册中心），文件数少属正常
- 文件数/行数超阈值但服务内包结构清晰、单一业务上下文 → 标记为"待确认"而非直接报 Blocker

**严重级别**：Critical

**解决方案与最佳实践**：
1. 按 DDD 限界上下文重新划分服务边界，一个服务对应一个业务子域
2. 对过大服务：识别内部领域边界，按子域拆分为独立服务
3. 对纳米服务：合并同子域的过细服务，减少运维与通信成本
4. 服务命名应体现业务领域（`order-service` 而非 `biz-service`）

---

## M-02 服务间通信效率

**判定目标**：服务间同步调用链路是否过长、是否存在可异步化的强同步依赖、循环调用。

**命中条件**：
- 同步调用链路深度 ≥ 3 跳（A→B→C→D），基于 `service-call-graph.json` 最长路径分析
- 服务间存在循环调用（A→B→A），DFS 检测调用图存在环
- 强同步依赖但场景为"通知/审计/日志"类（可解耦为消息异步）——通过调用方法语义判断（含 `notify`/`audit`/`log`/`metric` 等关键词的 Feign 调用）
- 高频调用：同一 Feign 接口在循环或多处高频被调用

**排除条件**：
- 链路深度大但每跳都为强一致核心业务（如订单→支付→库存，需同步保证）→ 标记"待确认"
- 循环调用经核对实为查询类只读调用且无写操作 → 降级为 Major 并提示

**严重级别**：Major（循环调用升 Critical）

**解决方案与最佳实践**：
1. 调用链路 ≥3 跳：引入聚合服务层或 BFF，将串行同步改为并行调用
2. 通知/审计类依赖：改用消息队列（Kafka/RocketMQ）异步解耦
3. 循环调用：重构服务边界，消除环依赖；或引入事件驱动解耦
4. 高频调用：引入本地缓存或聚合接口，减少跨服务往返

## M-03 数据一致性（共享业务库）

**判定目标**：是否多服务直连同一业务数据库，破坏服务自治。

**命中条件**：
- 解析各服务 `application.yml`/`application.properties` 的 `spring.datasource.url`，多个服务的 URL 指向同一库（host+port+库名一致）
- 服务直接 import 其他服务的 Mapper/Repository/DAO 包（`import com.xxx.order.mapper.*` 出现在 payment 服务）
- 跨服务联表查询：SQL/XML 中出现其他服务领域的表名（需结合表名-服务归属映射判断）

**排除条件**：
- 共享的是只读配置库/字典库/公共元数据 → 不报（属合理共享）
- 多服务共享库但经核对为过渡期单体改造遗留，且已纳入拆分计划 → 标记"待确认"

**严重级别**：Blocker

**解决方案与最佳实践**：
1. 每个服务独占自己的数据库，跨服务数据通过 API 获取
2. 共享配置/字典数据：抽取为独立配置服务或配置中心
3. 跨服务联表查询：改为服务间 API 调用后在应用层聚合，或引入 CQRS 读模型
4. 过渡期：为共享库建立拆分计划表，逐步迁移表归属

## M-04 分布式事务缺失

**判定目标**：跨服务写操作是否有一致性保障方案。

**命中条件**：
- 存在跨服务写操作链路（一个业务流程中 A 服务写本地库后调用 B 服务写库），且：
  - 无 TCC/Saga/seata 注解（`@GlobalTransactional`、`@TwoPhaseBusinessAction`、`@LcnTransaction`）
  - 无消息最终一致性方案（无 `@RocketMQTransactionListener`/事务消息发送）
  - 无本地消息表/对账补偿机制代码痕迹
- 单服务内 `@Transactional` 标注的方法中存在跨服务 Feign/Dubbo 调用（本地事务无法覆盖远程调用）

**排除条件**：
- 跨服务调用为只读查询 → 不报
- 调用虽有写但业务上允许最终一致且已有对账机制 → 标记"待确认"

**严重级别**：Critical

**解决方案与最佳实践**：
1. 强一致场景：引入 Seata AT/TCC 模式，跨服务写加 `@GlobalTransactional`
2. 最终一致场景：使用事务消息（RocketMQ 事务消息）+ 本地消息表 + 消费幂等
3. 可补偿场景：Saga 模式，每步定义正向操作与补偿操作
4. 禁止依赖 `@Transactional` 解决跨服务事务——本地事务边界不覆盖 RPC

---

## M-05 容错熔断缺失

**判定目标**：服务间调用是否有熔断、降级、超时、重试控制。

**命中条件（Feign）**：
- 存在 `@FeignClient` 接口，但未配置 `fallback`/`fallbackFactory`
- Feign 调用未配置超时（`feign.client.config.default.connectTimeout/readTimeout` 缺失，或 Ribbon 超时缺失）
- 使用 Hystrix 但未启用 `@EnableCircuitBreaker`，或 `@FeignClient` 未启用熔断

**命中条件（Dubbo）**：
- `@DubboReference`/`@Reference` 未配置 `mock`（降级）或 `timeout`（超时）
- 未配置 `retries` 上限（默认重试可能导致写操作重复）

**命中条件（RestTemplate/WebClient）**：
- 直接 `new RestTemplate()` 未配置超时与连接池
- 调用未包裹熔断器（无 `@HystrixCommand`/`@SentinelResource`）

**排除条件**：
- 调用方为网关/纯路由转发服务，熔断由网关统一处理 → 不在服务侧重复报
- 调用为本地内部模块调用（非跨服务）→ 不报

**严重级别**：Critical

**解决方案与最佳实践**：
1. 所有 Feign 客户端配置 `fallbackFactory`（而非 fallback，以获取异常原因）
2. 全局配置超时：连接超时 2s、读超时 5s（按业务调整）
3. 写操作接口 `retries=0`，避免重复写入；读操作可重试但设上限
4. 关键链路用 Sentinel 配置熔断规则（慢调用比例/异常比例熔断）
5. 降级逻辑返回兜底数据而非直接抛错，保证核心链路可用

## M-06 API 网关配置

**判定目标**：网关是否配置限流、鉴权、路由安全。

**命中条件**：
- 工程含 Spring Cloud Gateway/Zuul 网关服务，但：
  - 路由配置中内部服务直接暴露无鉴权 filter
  - 未配置限流（无 `RequestRateLimiter`/Sentinel 网关流控）
  - 未配置全局鉴权 filter（无 `GlobalFilter` 实现鉴权逻辑）
  - 未配置 CORS 或 CORS 配置为 `*`（允许任意来源）
  - 网关未配置超时与请求体大小限制

**排除条件**：
- 网关后端服务为内部管理后台，已有独立鉴权 → 降级提示
- 网关仅为内部服务网关不对外 → 限流/鉴权可放宽，标记"待确认"

**严重级别**：Major

**解决方案与最佳实践**：
1. 网关统一鉴权：实现 `GlobalFilter` 校验 JWT/Token，未通过直接 401
2. 全局限流：Sentinel 网关流控或 `RequestRateLimiter` + Redis，按 API 维度限流
3. 路由最小暴露：仅对外暴露必要路由，内部服务路由不对外
4. CORS 白名单：明确允许的来源，禁止 `*`
5. 配置请求超时与请求体大小上限，防止慢速攻击

## M-07 服务注册发现

**判定目标**：是否通过注册中心发现服务，而非硬编码地址。

**命中条件**：
- 源码或配置中出现硬编码 IP/域名调用（`http://192.168.x.x`、`http://order-service:8081` 直连，绕过注册中心）
- 使用 `RestTemplate` 直连 URL 而非服务名（`http://ORDER-SERVICE` 走负载均衡）
- Dubbo `@DubboReference` 直连配置（`url=` 直连）出现在生产配置

**排除条件**：
- 硬编码地址在测试/本地 profile（`application-local.yml`）→ 不报
- 调用外部第三方系统（非内部服务）必须直连 → 不报

**严重级别**：Major

**解决方案与最佳实践**：
1. 内部服务调用一律走注册中心（Nacos/Eureka）服务发现
2. RestTemplate 加 `@LoadBalanced`，用服务名调用
3. Dubbo 不配置直连 url，走注册中心
4. 多环境用不同 namespace/group 隔离

## M-08 配置管理

**判定目标**：敏感配置是否安全管理，多环境配置是否一致。

**命中条件**：
- 源码中硬编码密钥/连接串/Token（正则匹配 `password=`、`secret=`、`accessKey=`、长 Base64 串等）
- 数据库密码、Redis 密码明文写在 `application.yml`（非环境变量引用 `${DB_PASSWORD}`）
- 未使用配置中心（Nacos/Apollo）管理，多环境配置散落多个文件且易不一致

**排除条件**：
- 明文配置为本地开发默认值且在 `application-local.yml` → 不报但提示
- 使用了 `${ENV_VAR}` 占位引用 → 视为安全实践，不报

**严重级别**：Major（硬编码密钥升 Blocker）

**解决方案与最佳实践**：
1. 所有敏感配置走配置中心（Nacos/Apollo），按环境隔离
2. 密钥用环境变量或密钥管理服务（KMS）注入，源码不留明文
3. 配置中心启用鉴权与加密（Nacos 配置加密）
4. 建立 `application.yml` 审查清单，禁止提交明文密钥（pre-commit 钩子）

---

## M-09 接口幂等性

**判定目标**：写接口是否做幂等设计，防止重复提交/重试导致脏数据。

**命中条件**：
- POST/PUT 写接口（Controller 方法标注 `@PostMapping`/`@PutMapping`）：
  - 未使用幂等键（无 `@Idempotent` 注解、无 `RequestId`/`traceId` 幂等校验）
  - 无唯一约束/分布式锁防重
- Feign/Dubbo 调用配置了重试（`retries>0`）但被调接口无幂等保障

**排除条件**：
- 接口本质天然幂等（纯删除 `DELETE /{id}`、纯更新覆盖写）→ 不报
- 只读 GET 接口 → 不报

**严重级别**：Critical

**解决方案与最佳实践**：
1. 写接口加幂等键：客户端生成 requestId，服务端 Redis SETNX 去重
2. 数据库唯一约束兜底防重
3. 关键写操作分布式锁（Redisson）防并发重复
4. 重试接口必须幂等：要么接口幂等，要么 retries=0

---

## M-10 API 版本管理

**判定目标**：对外 API 是否有版本管理。

**命中条件**：
- 对外 Controller 路径无版本号（`/api/order` 而非 `/api/v1/order`）
- 现有 API 发生破坏性变更（参数增删/返回结构变更）但未新增版本路径

**排除条件**：
- 内部服务间调用 API，无外部消费者 → 降为 Minor 提示
- 灰度期接口已有兼容策略 → 标记"待确认"

**严重级别**：Minor

**解决方案与最佳实践**：
1. 对外 API 路径带版本号 `/api/v1/xxx`
2. 破坏性变更新增版本，旧版本保留至少一个迭代并标注废弃
3. 用 Header 版本协商（`Accept: application/vnd.xxx.v2+json`）或路径版本

## 人工复核清单（脚本无法判定的语义级问题）

脚本产出疑似线索后，由审查者逐项确认。以下问题需人工判断：

- [ ] 领域边界是否清晰（M-01）：服务内是否单一业务上下文
- [ ] 强同步是否必要（M-02）：调用链是否可异步化
- [ ] 共享库是否过渡期（M-03）：是否已纳入拆分计划
- [ ] 跨服务写是否真需强一致（M-04）：业务上是否允许最终一致
- [ ] 降级逻辑是否合理（M-05）：fallback 返回值是否业务可用
- [ ] 网关是否对外（M-06）：是否需要严格限流鉴权

**确认原则**：仅当人工确认命中后，才将问题计入正式报告，避免误报。
