# PM制品与交付

用于完整PM制品生命周期的压缩参考：从原型人物和问题框架到PRD、用户故事、史诗、故事地图和生命周期结束沟通。

## PRD开发

10个部分的文档，构建需2-4天。

**模板结构（10个部分）：**
1. 执行摘要 -- "我们正在为[人物角色]构建[解决方案]以解决[问题]，最终[影响]。"
2. 问题陈述 -- 谁、什么、为什么、证据（引语、分析、工单）
3. 目标用户和人物角色 -- 主要+次要原型人物
4. 战略上下文 -- OKR、TAM/SAM/SOM、竞争格局、"为什么是现在？"
5. 解决方案概述 -- 高级描述+用户流程（不是像素规格）
6. 成功指标 -- 主要指标（优化）、次要指标（监控）、护栏指标（不回归）
7. 用户故事和需求 -- 史诗假设+拆分的带有验收标准的故事
8. 范围外 -- 明确的排除及理由
9. 依赖和风险 -- 技术、外部、团队；风险+缓解
10. 开放问题 -- 需要发现解决的未决决策

**指标结构：** 始终定义当前基线、目标和测量时间线。格式："指标：从当前X -> 目标Y，上线Z天后测量。"

**阶段顺序：**
- 第1天：执行摘要（30分钟）+ 问题（60分钟）+ 人物角色（30分钟）+ 策略（45分钟）
- 第2天：解决方案（60分钟）+ 指标（30分钟）+ 故事（90-120分钟）
- 第3天：范围/依赖（30分钟）+ 评审（60分钟）

## 用户故事

**格式（Mike Cohn + Gherkin）：**
```
作为一个[具体人物角色]，我想要[行动]，以便[成果/动机]。

场景：[描述]
假设：[前置条件——多个假设都可以]
当：[单个触发事件——对应"我想要"]
然后：[单个成果——对应"以便"]
```

**质量门：**
- "作为一个"使用具体人物角色，不是通用的"用户"
- "以便"陈述动机，不是行动的重复陈述
- 一个当、一个然后。多个=拆分信号。
- 验收标准可被QA测试——没有"更好的体验"或"更快"
- 摘要以价值为中心："为试用用户启用Google登录"不是"添加登录按钮"

### 拆分故事

8种模式按顺序应用（Richard Lawrence / Humanizing Work）。在第一个匹配时停止：

| # | 模式 | 信号 | 拆分策略 |
|---|------|------|----------|
| 1 | 工作流步骤 | 多步骤序列 | 薄端到端切片（完整工作流，增加复杂性） |
| 2 | 业务规则 | 每个场景不同规则 | 每个规则变体一个故事 |
| 3 | 数据变体 | 不同数据类型/格式 | 每个数据类型一个故事，从最简单的开始 |
| 4 | AC复杂性 | 多个当/然后 | 每个当/然后对一个故事 |
| 5 | 主要努力 | 首先构建困难，添加容易 | "实现一个 + 添加剩余的" |
| 6 | 外部依赖 | 多个API/第三方 | 每个依赖边界一个故事 |
| 7 | DevOps步骤 | 基础设施/部署工作 | 按运营复杂性拆分 |
| 8 | 发现的微小行为 | 高度不确定性，以上都不适用 | 时间盒实验，不是故事 |

**拆分后验证：** 每部分必须(a)独立交付用户价值，(b)独立可测试，(c)适合冲刺（1-5天），(d)所有部分组合等于原始。

**关键规则：** 始终垂直拆分（前端+后端=用户价值）。永远不要水平拆分（"构建API" / "构建UI"）。

## 故事映射

**Jeff Patton框架——2D地图：**
- 水平（从左到右）：按叙事/工作流顺序的活动 = 主干
- 垂直（从上到下）：每个活动内的优先级

**层次结构：** 细分 -> 人物角色 -> 叙事（目标）-> 活动（3-5）-> 步骤（每个活动3-5）-> 任务（每个步骤5-7）

**构建地图：**
1. 定义细分 + 人物角色 + 叙事（单句JTBD目标）
2. 按顺序工作流识别3-5个主干活动
3. 将每个活动拆分为步骤（用户行动、可观察、合乎逻辑的顺序）
4. 将步骤拆分为任务（粒度化、可优先级化）
5. 垂直优先级：顶部 = MVP，中间 = R2，底部 = 未来
6. 画水平发布线

**行走骨架：** 每个活动的最高优先级任务 = 最小端到端功能。跨所有活动增量构建，而不是在开始下一个之前完成一个活动。

**发布切片：**
- R1（行走骨架）：所有活动中最简单的版本
- R2（增强）：改进核心工作流的第二优先级任务
- R3（完善）：锦上添花、边缘情况、优化

## 史诗

### 史诗假设

**模板（Tim Herbig / 精益UX）：**
```
如果我们[具体行动/解决方案]
用于[具体人物角色]
那么我们将[可衡量成果]
```

**发现的微小行为：** 在完全构建前2-3个轻量级实验。
- 类型：原型+用户测试、礼宾服务测试、着陆页测试、巫术测试、A/B测试
- 约束：天/周不是月；便宜；可证伪

**验证措施：**
```
如果我们在[2-4周]内观察到以下情况，我们就知道假设是有效的：
- [定量："激活率增加20%"]
- [定性："10个用户中8个说节省了时间"]
```

**决策门槛：** 验证 -> 写用户故事。无效 -> 杀死或转向。不确定 -> 更多实验。

### 史诗拆分（9种模式）

预拆分：INVEST检查（独立性、可协商性、价值性、可估算性、规模性、可测试性）。如果没有价值，停止——与其他工作合并，不要拆分。

**9种模式顺序应用**（故事拆分的超集）：
1. **工作流步骤** -- 薄端到端，不是逐步
2. **操作（CRUD）** -- "管理" = 创建 + 读取 + 更新 + 删除
3. **业务规则变体** -- 每个规则 = 独立故事
4. **数据变体** -- 及时添加数据类型
5. **数据输入方法** -- 首先基本输入，以后花哨UI
6. **主要努力** -- 实现一个 + 添加剩余的
7. **简单/复杂** -- 首先最简单的核心，以后变体
8. **延迟性能** -- "先让它工作"然后"让它快速"
9. **拆分spike** -- 当不确定性阻止拆分时时间盒调查

**跨所有内容的元模式：** 识别核心复杂性 -> 列出变体 -> 减少到一个完整切片 -> 使其他变体成为独立故事。

**评估拆分：** (a)它是否揭示了可以杀死的低价值工作？(b)结果故事大致相等规模？

**Cynefin调整：** 低不确定性 = 找到所有故事，按价值优先级。高不确定性 = 仅识别1-2个学习故事。混乱 = 延迟拆分，先稳定。

## 原型人物

**假设驱动的人物角色，不是验证的研究。** 从可用数据在几小时内创建。

**模板部分：**
1. **名字** -- 押韵的、易记的（"经理Mike"）
2. **简历和人口统计** -- 行为的，不只是年龄/位置。包括职业、在线存在、技术习惯。
3. **引语** -- 真实的或代表性的；揭示心态，不是事实
4. **痛点** -- 具体和产品相关（"每周3小时在工具之间复制数据"）
5. **他们试图完成什么** -- 可观察的行为和成果
6. **目标** -- 短期+长期，个人+职业
7. **态度和影响因素** -- 决策权威、影响者、影响采用的信念

**标记不确定性：** 用[假设——验证]标记未验证项。计划研究以填补空白。最初限制为1-2个人物角色。

## 新闻稿/PRFAQ

**亚马逊逆向工作格式。** 在构建前编写。规划工具，不是发布文案。

**结构：**
1. **标题** -- 利益聚焦、具体（"将发票处理减少60%"）
2. **日期行** -- 城市、日期
3. **介绍** -- 什么发布了、针对谁、关键收益（2-3句）
4. **问题段** -- 带数据的具体客户问题
5. **解决方案段** -- 以成果为中心，不是功能列表
6. **高管引语** -- 客户同理心、有远见（不是"很兴奋创新"）
7. **支持细节** -- 带数据的额外收益
8. **样板文本** -- 公司背景
9. **CTA + 媒体联系**

**试金石测试：** 客户会关心吗？问题清楚吗？收益可衡量吗？无行话？能经受"那又怎样"？

## 故事板

**6帧叙事弧** 用于推销、对齐和情感验证。

| 帧 | 名称 | 内容 |
|----|------|------|
| 1 | 主角 | 人物角色+上下文（具体，不是"忙碌的专业人士"） |
| 2 | 问题出现 | 挑战+如何影响生活 |
| 3 | "哦糟"时刻 | 造成紧迫性的升级 |
| 4 | 解决方案出现 | 产品的现实发现 |
| 5 | "啊哈"时刻 | 突破体验（成果，不是功能演示） |
| 6 | 之后的生活 | 改进状态带具体性 |

**视觉风格默认：** 粗头马克笔素描，最小化，单色。低 fidelity 没关系。

**7个输入问题：** 角色是谁？什么问题？什么升级？解决方案如何引入？突破是什么？之后的生活是什么？视觉风格偏好？

## 推荐画布

**11部分战略提案** 用于AI/高不确定性产品决策。 executive友好。

1. **业务成果** -- [方向] [指标] [成果] [上下文] [标准]
2. **产品成果** -- 相同格式，客户视角
3. **问题陈述** -- 人物角色为中心的叙事
4. **解决方案假设** -- If/Then + 发现的微小行为 + 生命周期证明措施
5. **定位陈述** -- For/That需要/Is a/That + Unlike/Provides差异化
6. **假设和未知** -- 明确的、可测试的
7. **PESTEL风险（调查）** -- 政治、经济、社会、技术、环境、法律（具体，不是通用）
8. **PESTEL风险（监控）** -- 较低优先级的观察列表
9. **价值论证** -- C级支持的数据驱动案例（"解决第一痛点，50万美元ARR影响"）
10. **成功指标** -- SMART格式
11. **下一步** -- 有序行动步骤

## 生命周期结束沟通

**9部分同理心优先的EOL消息。** 没有完整过渡计划绝不发送。

**结构：**
1. **公司上下文** -- 你是谁，客户承诺
2. **公告** -- 单个清晰句子：什么结束、什么替代、何时
3. **理由** -- 框架为客户收益，不是成本节省
4. **当前产品上下文** -- 承认正在失去什么及它服务谁
5. **客户影响** -- 明确命名中断（迁移时间、学习曲线、集成更新）
6. **过渡解决方案** -- 定位格式：For/That currently use/Is a/That + 连续性 + 改进
7. **支持措施** -- 一对一帮助、自动迁移、折扣、培训
8. **时间线** -- 具体日期：迁移工具可用、只读日期、完全关闭、数据导出截止。提前6-12个月通知。
9. **行动号召** -- 下一步+联系信息

**语气规则：** 有同理心，不是防御。向前看，不是道歉。具体，不是模糊。永远不要因为低使用率责怪客户。

## 质量门

### 跨切反模式

| 反模式 | 出现在 | 修复 |
|--------|--------|------|
| 孤立编写 | PRD、故事地图 | 在故事/地图上与设计和工程协作 |
| 问题陈述无证据 | PRD、新闻稿、画布 | 包含引语、分析、工单 |
| 解决方案过于规定性 | PRD | 保持解决方案高级；让设计拥有UI |
| 功能列表而不是收益 | 新闻稿、画布 | 将功能翻译为成果 |
| 通用"作为一个用户" | 用户故事 | 使用具体人物角色名字/角色 |
| "以便"重复"我想要" | 用户故事 | 挖掘真正动机 |
| 多个当/然后 | 用户故事 | 拆分故事 |
| 水平切片 | 故事拆分、史诗拆分 | 始终垂直：每个故事交付端到端用户价值 |
| 跳过实验 | 史诗假设、画布 | 构建前定义轻量级验证 |
| 模糊验证措施 | 史诗假设、画布 | 具体指标+时间线（2-4周） |
| 把假设当承诺 | 史诗假设 | 框架为赌注；允许无效 |
| 活动是功能，不是行为 | 故事地图 | 映射用户行动，不是产品能力 |
| 技术主干 | 故事地图 | 主干跟随用户工作流，不是系统层 |
| 功能完整的瀑布发布 | 故事地图 | 行走骨架 = 跨所有活动薄切片 |
| 人口统计没有行为 | 原型人物 | 添加行为上下文，不只是年龄/位置 |
| 太多人物角色 | 原型人物 | 从1-2个开始；验证后扩展 |
| 商业为中心的EOL理由 | EOL消息 | 框架为客户收益 |
| 模糊EOL时间线 | EOL消息 | 带里程碑的具体日期 |
| 无过渡支持计划 | EOL消息 | 迁移帮助、工具、折扣 |
