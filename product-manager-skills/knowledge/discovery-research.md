# 发现与研究

用于端到端运行产品发现过程的压缩决策逻辑、框架和质量门：框架问题、访谈客户、映射工作与旅程、生成解决方案，以及在投入开发前验证假设。

## 问题框架

### 问题陈述（组件）

**模板——从用户视角书写：**

```
我是一个：      [具有3-4个关键特征的人物角色]
正在尝试：      [期望成果——可衡量的，不是任务]
但是：          [阻止成果实现的障碍]
因为：          [根本原因，不是症状]
这让我感到：    [来自研究中的真实情感]
```

**最终陈述公式：** `[人物角色]需要一个[成果]的方式，因为[根本原因]，目前[影响]。`

**质量门：**
- "我是一个"通过的标准是你能想象一个真实的人（不是"忙碌的专业人士"）
- "正在尝试"是成果，不是活动
- "因为"能经受住5个为什么的追问
- "让我感到"使用verbatim客户语言，不是营销文案
- 最终陈述适合一句话且可衡量

**主要反模式：**
1. **方案走私** -- "问题是我们没有X。"修复：以用户成果为框架重新表述。
2. **伪装成用户问题的业务问题** -- "用户希望降低我们的流失。"修复：从用户视角深入挖掘为什么他们离开。
3. **症状而非根本原因** -- "因为UI令人困惑。"修复：持续问"为什么"直到找到结构性原因。

---

### 问题框架画布（MITRE，交互式）

**写问题陈述前的三阶段偏见检查。**

**阶段1——向内看：**
- 问题是什么？（仅症状）
- 为什么我们还没有解决它？（新的/困难的/低优先级的/缺乏资源的/缺乏权威的/系统性不公平）
- 我们如何成为问题的一部分？（确认偏见/内部偏见/幸存者偏见/过早收敛）

**阶段2——向外看：**
- 谁经历了它？何时、何地、后果？
- 谁还有这个问题？谁没有？（反例揭示根本原因）
- 谁被排除在对话之外？
- 谁从问题的存在中受益？谁从解决问题中受益？

**阶段3——重新框架：**
- 重述："[谁]难以[什么]因为[根本原因]，导致[后果]。影响[细分市场]，因为[偏见]被忽视。"
- HMW："我们如何能够[行动]同时瞄准[目标]？"

**质量门：**
- HMW足够宽泛以允许多个解决方案，足够窄以可操作
- 画布是跨职能完成的，不是独自完成的
- "谁从现状中受益？"被明确回答

**主要反模式：**
1. **跳过向内看** -- 群体思维持续存在。修复：强制明确的偏见讨论。
2. **通用重新框架** -- "改善用户体验。"修复：包含谁、什么、何时、后果、根本原因。
3. **HMW太窄** -- "我们如何添加一个移动应用？"修复：陈述工作，而不是解决方案。

## 客户发现

### 发现过程（工作流，6阶段/3-4周）

```
阶段1：框架（第1-2天）
  -> 问题框架画布（120分钟）+ 问题陈述（30分钟）
  -> 可选：原型人物，JTBD
  -> 输出：问题假设，3-5个研究问题，成功标准
  -> 门槛：有足够的上下文开始研究吗？如果没有，先收集数据（+2-3天）

阶段2：规划研究（第3天）
  -> 发现访谈准备（90分钟）
  -> 招募5-10个参与者，在1-2周内安排
  -> 输出：访谈指南（5-7个Mom Test问题），参与者名单

阶段3：进行研究（第1-2周）
  -> 5-10次访谈 + 支持工单分析 + 分析审查
  -> 每次访谈的笔记模板：参与者、情境、行动、痛点、变通方案、verbatim引语、洞察
  -> 门槛：饱和？3次以上访谈中相同的痛点 = 继续。仍在学习 = +3-5次访谈。

阶段4：综合（第2周末）
  -> 亲和图：便利贴 -> 带有频率计数的主题集群
  -> 可选：客户旅程图工作坊
  -> 优先级：按频率 x 强度 x 战略契合度对每个痛点评分（每项1-5）
  -> 输出：前3-5个痛点，每个痛点3-5条verbatim引语，验证的问题陈述

阶段5：生成和验证解决方案（第3周）
  -> 机会解决方案树或精益UX画布
  -> 设计实验：礼宾服务/原型/着陆页/A/B测试
  -> 运行实验（每个1-2周）
  -> 门槛：验证了？如果没有，转向下一个解决方案（+1-2周）

阶段6：决定和记录（第3-4周）
  -> GO（路线图 + 史诗 + PRD）/ PIVOT（下一个解决方案）/ KILL（降低优先级）
  -> 30分钟利益相关者汇报：问题验证、解决方案验证、建议
```

**时间线范围：** 快轨3周（5次访谈，1个实验）| 典型4周 | 彻底6-8周。

**主要反模式：**
1. **跳过访谈** -- 仅依赖分析。修复：始终进行5-10次定性访谈。
2. **分析瘫痪** -- 6周综合。修复：时间盒到总共3-4周。
3. **一次性发现** -- 运行持续的（Teresa Torres：每周1次访谈）。

---

### 访谈准备（交互式，4个自适应问题）

**Q1——研究目标：** 问题验证 | JTBD发现 | 留存/流失调查 | 功能优先级

**Q2——目标细分：** 定期经历问题的人 | 尝试解决问题的人 | 目标细分中的人无论是否意识到 | 最近经历问题的人

**Q3——约束：** 有限访问（5-10，2周）| 现有客户群（100+）| 需要冷接触 | 仅内部利益相关者（代理）

**Q4——方法论（基于Q1-Q3的上下文感知）：**
- **Mom Test（Rob Fitzpatrick——问题验证）：** 过去行为，不是假设。"告诉我上一次..."
- **JTBD访谈：** 客户雇佣/解雇什么。"你试图完成什么？"
- **Switch访谈：** 改变解决方案的推/拉。"是什么促使你寻找？"
- **时间线/旅程映射：** 完整体验的按时间顺序的演练

**输出：访谈计划，包括开场（5分钟）、5个核心问题及追问和反模式、结尾（5分钟）、偏见检查清单、成功标准和后勤。**

**每个访谈中要避免的5种偏见：**
1. 确认偏见 -- 不要问"你不认为X是个问题吗？"
2. 引导性问题 -- 不要问"你会使用这个吗？"
3. 假设性问题 -- 不要问"如果我们构建Y，你会付钱吗？"
4. 伪装成研究的推销 -- 不要解释你的解决方案
5. 是/否问题 -- 不要问"开票困难吗？"

**访谈成功 = 具体故事（不是泛泛抱怨）+ 过去行为（不是愿望）+ 3次以上访谈中的模式 + 至少一个惊喜。**

**主要反模式：**
1. **问客户想要什么** -- 得到功能请求，不是问题。修复：问过去行为。
2. **推销而不是倾听** -- 前5分钟不要提你的解决方案（如果真要提的话）。
3. **停在1-2次访谈** -- 小样本 = 确认偏见。修复：最少5-10次。

## 待完成工作

### JTBD框架（组件）

**客户工作的三个类别：**

| 类型 | 问题 | 示例 |
|------|------|------|
| **功能型** | 完成什么任务？ | "对税务申报对账月度开支" |
| **社交型** | 如何被看待？ | "被高管团队视为有战略眼光" |
| **情感型** | 达到/避免什么状态？ | "对不错过细节感到有信心" |

**四类痛点：**
- **挑战：** 阻止工作完成的障碍
- **代价高：** 过量的时间、金钱或努力
- **常见错误：** 可预防的错误
- **未解决的问题：** 当前解决方案中的差距

**四类收益：**
- **期望：** 超出当前解决方案的
- **节省：** 时间/金钱/努力的减少
- **采用因素：** 触发切换的
- **生活改善：** 生活如何变得更好

**工作质量门：**
- 动词驱动（动作，不是名词）
- 解决方案不可知（"与团队沟通"而不是"使用Slack"）
- 具体（"为税务扣除跟踪开支"而不是"管理财务"）

**优先级：** 按强度对痛点排序（急性vs.轻度）。问："如果我们解决一个痛点，哪个影响最大？"

**主要反模式：**
1. **将工作与解决方案混淆** -- "我需要Slack。"修复：问5次"为什么"。
2. **忽视社交/情感工作** -- 人们的购买基于情感，用逻辑证明。修复：明确询问看法和感受。
3. **没有研究就编造JTBD** -- 假设不是洞察。修复：进行switch访谈或情境查询。

## 机会映射

### 机会解决方案树（Teresa Torres——交互式，2阶段）

**结构：**
```
期望成果（1个可衡量指标）
    |
    +-- 机会1（客户问题，不是解决方案）
    |     +-- 解决方案A + 实验
    |     +-- 解决方案B + 实验
    |     +-- 解决方案C + 实验
    |
    +-- 机会2
    |     +-- 解决方案...
    |
    +-- 机会3
          +-- 解决方案...
```

**阶段1——生成树：**
1. 提取期望成果（收入增长/留存/获客/效率）
2. 每个成果生成3个机会（有证据的客户问题）
3. 每个机会生成3个解决方案（每个都有假设+实验）

**阶段2——选择POC：**
- 对每个解决方案评分：可行性（1-5）+ 影响（1-5）+ 市场契合度（1-5）
- 可行性：1 = 月，5 = 天 影响：1 = 最小，5 = 重大 市场契合度：1 = 客户不在乎，5 = 主动要求
- 选择总分最高的作为POC。定义实验类型：A/B测试、原型+可用性，或礼宾服务。

**假设模板：** "如果我们[解决方案]，[指标]将从[X]变为[Y]因为[理由]。"

**主要反模式：**
1. **伪装成解决方案的机会** -- "我们需要移动应用。"修复：重新框架为客户问题："移动用户无法随时访问产品。"
2. **跳过发散** -- "我们知道解决方案。"修复：每个机会生成3个以上。强制收敛前发散。
3. **没有实验** -- 选择解决方案然后进入路线图。修复：每个解决方案必须映射到实验。
4. **模糊成果** -- "改善UX。"修复：使其可衡量："将流失从60%降低到40%。"

## 客户旅程

### 旅程图（组件）

**横轴（阶段）：** 认知 -> 考虑 -> 决策 -> 服务 -> 忠诚

**纵轴（每阶段）：**
- 客户行动（可观察的、具体的）
- 触点（数字+物理+人工）
- 客户体验（带有客户引语的情感）
- KPI（可衡量的、阶段适当的）
- 业务目标（成果导向、与阶段一致）
- 涉及的团队（跨职能与特定角色）

**质量门：**
- 情感是具体的（"松了一口气，设置花了30分钟，而不是3小时"）不是通用的（"高兴"）
- 触点包括线下（会议、电话），不仅仅是数字
- 地图反映客户实际做的，不是你希望他们做的
- 每个阶段都有KPI和目标

---

### 旅程映射工作坊（交互式，5个问题）

**Q1——行动者：** 选择人物角色（主要/次要/高流失/新发现的）
**Q2——场景+目标：** 首次使用/核心工作流/问题解决/升级扩展
**Q3——旅程阶段：** 基于场景生成4-6个阶段（例如，发现 -> 评估 -> 试用 -> 激活 -> 使用 -> 扩展）
**Q4——每阶段映射：** 每阶段3-5个行动、想法、情感和痛点
**Q5——机会：** 按影响对5-7个痛点排序（高/中/低）并提供证据

**输出：** 完整旅程图 + 优先级机会列表。

**主要反模式：**
1. **映射内部流程，不是客户体验** -- "线索生成 -> 资格认定 -> 演示。"修复：从客户视角映射。
2. **没有情感** -- 只有行动。修复：添加客户引语和情感状态。
3. **一个人物角色地图太多** -- 失去焦点。修复：每个人物角色一张地图。

## 精益验证

### 精益UX画布（v2，交互式，8个框）

**填写顺序：**

| 框 | 问题 | 内容类型 |
|-----|------|----------|
| 1. 业务问题 | 什么变化创造了问题？ | 上下文+触发器 |
| 2. 业务成果 | 什么行为改变 = 成功？ | 指标（不是情感） |
| 3. 用户 | 首先针对哪个人物角色？ | 特定细分 |
| 4. 用户成果和收益 | 用户为什么会寻求这个？ | 目标、情感、同理心（不是指标） |
| 5. 解决方案 | 什么可能解决它？ | 3个以上候选功能/计划 |
| 6. 假设 | 可测试的if/then陈述 | "我们相信[成果]如果[用户]通过[解决方案]获得[收益]" |
| 7. 首先学习 | 什么是最有风险的假设？ | 价值 > 可用性 > 可行性 > 可行性风险 |
| 8. 最小工作 | 测试它的最小实验？ | 必须在<2周内完成 |

**框2 vs 框4区别：** 框2 = 行为改变指标。框4 = 人类动机和同理心。

**主要反模式：**
1. **从解决方案开始** -- 框1说"构建X"。修复：问"什么改变了？为什么现在这是个问题？"
2. **混淆框2和框4** -- 在同理心框里放指标。修复：框2 = 数字，框4 = 感受。
3. **框5只有一个解决方案** -- 没有探索。修复：强制3个以上候选。
4. **跳过实验** -- "直接构建。"修复：首先设计最小测试。

### PoL探测（组件）—— 生命周期证明

**一次性的、假设驱动的验证制品。不是MVP。计划删除。**

**5个必需特征：** 轻量级（小时/天）+ 可处置（设置删除日期）+ 窄范围（一个假设）+ 残酷诚实（揭示残酷真相）+ 小而专注（侦察，不是产品）。

**模板字段：** 假设、被消除的风险、探测类型、目标用户、成功标准（通过/失败/学习阈值）、工具、时间线、处置计划、负责人、状态。

**5种探测风格：**

| 风格 | 核心问题 | 时间线 | 何时使用 |
|------|----------|--------|----------|
| 可行性检查 | 我们能构建这个吗？ | 1-2天 | 技术未知、API依赖、数据完整性 |
| 任务聚焦测试 | 用户能完成这个工作吗？ | 2-5天 | 关键UI时刻、导航、流失区 |
| 叙事原型 | 这能赢得认同吗？ | 1-3天 | 复杂流程解释、利益相关者对齐 |
| 合成数据模拟 | 我们能在没有生产风险的情况下建模吗？ | 2-4天 | 边缘情况、未知-未知、负载测试 |
| 感觉编码探测 | 这能在真实用户接触中存活吗？ | 2-3天 | 需要真实交互的工作流/UX验证 |

**黄金法则：** 使用告诉最残酷真相的最便宜原型。

---

### PoL探测顾问（交互式，决策逻辑）

**选择流程：** 假设 -> 风险类型 -> 核心问题 -> 推荐探测。

**决策矩阵：**
- 技术可行性未知 -> **可行性检查**（ spike-and-delete，API嗅探测试）
- 关键UI摩擦 -> **任务聚焦测试**（Optimal Workshop，UsabilityHub，Maze）
- 需要利益相关者对齐 -> **叙事原型**（Loom演示，幻灯片故事板）
- 边缘情况探索 -> **合成数据模拟**（蒙特卡罗，合成用户，LangFlow）
- 需要真实用户交互 -> **感觉编码探测**（ChatGPT Canvas + Replit + Airtable Frankensoft）

**当假设太宽时细化问题：**
1. 你能首先测试的最小东西是什么？
2. 失败是什么样的？
3. 这是在测试用户行为、技术可行性还是利益相关者对齐？选一个。

**主要反模式：**
1. **基于工具舒适度选择** -- "我会Figma，所以我要原型。"修复：将方法匹配到假设，不是技能组合。
2. **默认到代码** -- "让我们直接构建。"修复：问通往残酷真相的最便宜路径是什么。
3. **将感觉编码探测与MVP混淆** -- 范围蔓延，拒绝处置。修复：构建前设置处置日期。
4. **一次测试多个东西** -- 结果模糊。修复：一个探测，一个假设。
5. **没有成功标准** -- "我们看到时会知道。"修复：构建前定义通过/失败/学习。

## 质量门

### 跨所有11个技能的合并反模式

**问题框架失败：**
- 问题陈述中的方案走私
- 用户问题框架中的业务指标
- 通用人物角色（"忙碌的专业人士"）
- 跳过偏见检查（向内看）

**研究失败：**
- 引导性/假设性/是-否问题
- 伪装成研究的推销
- 停在1-2次访谈（需要最少5-10次）
- 不立即在访谈后记录洞察
- 从未达到饱和（3次以上访谈中相同模式）

**综合失败：**
- 分析瘫痪（6周以上，没有决定）
- 机会伪装成OST中的解决方案
- 无法衡量的模糊成果
- 反映内部一厢情愿而非客户现实的旅程图
- 通用情感（"高兴"）而不是具体状态

**验证失败：**
- 原型表演（不能教任何东西的令人印象深刻的演示）
- 基于工具舒适度而非假设选择验证方法
- 在一个实验中测试多个变量
- 没有预定义的失败标准
- 将可处置探测当作生产代码对待
- 一次性发现而非持续实践

### 通用质量检查

每个发现制品都应该通过这些：
1. **可证伪：** 你能描述失败是什么样的吗？
2. **有证据支持：** 基于客户研究，不是假设？
3. **具体：** 你能想象那个人、那个问题、那个指标吗？
4. **可操作：** 它是否告知具体的下一步？
5. **有时间盒：** 是否有防止无限探索的截止日期？
