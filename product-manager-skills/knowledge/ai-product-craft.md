# AI产品打造

用于AI产品经理的压缩决策逻辑：就绪度评估、上下文架构、编排模式和验证方法论。源自ai-shaped-readiness-advisor、context-engineering-advisor和pol-probe-advisor。

## AI形态就绪度

### AI优先 vs AI形态

| 维度 | AI优先（门槛） | AI形态（可防御） |
|------|----------------|-----------------|
| 心态 | 自动化现有任务 | 重新设计工作完成方式 |
| 目标 | 加快制品创建 | 压缩学习周期 |
| AI角色 | 任务助手 | 战略共同智能 |
| 测试 | 竞争对手通过增加人员复制 | 竞争对手必须重新设计整个组织 |

### 5个核心能力

**1. 上下文设计** — 构建人类和AI都信任的持久"现实层"。将AI注意力视为稀缺的。持久化约束 + 词汇表；其他一切按需检索。基础：如果缺失，所有其他能力都是脆弱的。

**2. Agent编排** — 可重复、可追溯的AI工作流（研究 -> 综合 -> 批评 -> 决策 -> 记录理由）。版本控制的提示。每个步骤显示其工作。一次性提示是战术的；编排的工作流是战略的。

**3. 成果加速** — 压缩学习周期，而不仅仅是任务速度。消除验证滞后（PoL探测在几天内，不是几周）。移除批准延迟（AI根据约束预验证）。减少会议开销（异步AI综合）。

**4. 团队AI促进** — AI作为共同智能运作，而不是责任盾牌。审查规范（AI输出 = 草稿）。证据标准（引用来源，拒绝"我认为"）。决策权威（AI推荐，人类决定）。挑战AI的心理安全。

**5. 战略差异化** — 竞争对手无法通过增加人员复制的新客户能力。需要完整组织重新设计才能复制的workflow rewiring。竞争对手无法匹配的经济学（通过AI的10倍成本优势）。

### 成熟度级别（每能力）

- **级别1 — AI优先：** 一次性提示，无结构，仅效率
- **级别2 — 兴起：** 一些保存的提示/模板，分散文档，适度收益
- **级别3 — 转型中：** 多步骤工作流，结构化上下文，学习周期压缩
- **级别4 — AI形态：** 自主编排工作流，持久现实层，可防御护城河

### 优先级依赖链

```
上下文设计（基础）
  └─> Agent编排（需要上下文）
        └─> 成果加速（需要编排）
              └─> 战略差异化（需要以上全部）
团队AI促进 ────（并行track，需要规模化）
```

如果上下文设计是级别1-2，先修复它。没有它，其他一切都是脆弱的。

## 上下文工程

### 上下文填充 vs 上下文工程

| 维度 | 填充 | 工程 |
|------|------|------|
| 心态 | 数量 = 质量 | 结构 = 质量 |
| 方法 | "以防万一添加一切" | "我要做什么决定？" |
| 持久化 | 持久化所有上下文 | 有意图地检索 |
| Agent链 | agent之间共享一切 | 每个agent有 bounded context |
| 失败响应 | 重试直到它工作 | 修复结构 |
| 经济模型 | 上下文作为存储 | 上下文作为注意力（稀缺） |

**为什么填充失败：** 准确性随着上下文增长显著下降 — 模型优先开始和结束，忽略中间（Liu等2023，"迷失在中间"）。死胡同和错误累积（上下文腐化）。重试变得正常化。

### 5个诊断问题

1. **这支持什么具体决定？** 不能回答 = 不需要它。
2. **检索可以替代持久化吗？** 即时优于始终可用。
3. **谁拥有上下文边界？** 没有所有者 = 无界增长。
4. **如果我们排除这个会失败什么？** 没有具体失败 = 删除它。
5. **我们在修复结构还是避免它？** 填充 often masks bad info architecture。

### 持久化 vs 检索规则

- **持久化（80%+交互）：** 核心约束、用户偏好、操作词汇表、不可协商的规则
- **检索（<20%交互）：** 项目详情、历史PRD、竞品分析、过去 transcripts
- **灰色地带（20-80%）：** 权衡检索延迟 vs 上下文窗口成本

### 两层记忆架构

**短期（对话式）：** 立即交互历史。单会话。总结/截断较旧部分。

**长期（持久）：** 约束注册表 + 操作词汇表 + 用户偏好。向量数据库用于语义检索。两个子类型：
- 声明性：事实（"我们遵循HIPAA"）
- 程序性：模式（"始终在可用性之前验证可行性"）

### 研究 -> 计划 -> 重置 -> 实现循环

核心上下文腐化预防模式：

1. **研究：** Agent收集数据。上下文变得大而乱。预期中。
2. **计划：** 综合为高密度SPEC.md/PLAN.md（真相来源）。
3. **重置：** 清除整个上下文窗口。不可协商。
4. **实现：** 全新会话，只有计划作为上下文。

**为什么它有效：** 消除上下文腐化、死胡同和目标漂移。Agent以压缩、高信号的上下文干净开始。

### 效率公式

```
上下文效率 = (准确性 x 连贯性) / (Token数 x 延迟)
```

关键发现：使用25%可用token的RAG保留95%准确性，同时减少延迟和成本。

### 上下文清单模板

```
始终持久化：约束（技术、法规）、用户偏好、词汇表
按需检索：历史PRD、transcripts、竞品分析
排除：30天以上的会议记录、完整代码库、营销材料
边界所有者：[姓名]
下次审查：[日期 + 90天]
```

## Agent编排

### 核心工作流模式

```
研究 -> 综合 -> 批评 -> 决策 -> 记录理由
```

每个步骤必须：可追溯（引用来源）、有界（自己的上下文窗口）、版本控制（Git中的提示）、一致（相同输入 -> 可预测过程）。

### 成熟度演进

1. **临时提示：** 根据需要输入ChatGPT。没有复用。
2. **保存的模板：** 可复用提示、自定义 AI 助手与项目。手动步骤。
3. **多步骤工作流：** 研究 -> 综合 -> 批评。步骤之间手动交接。
4. **自主编排：** 端到端运行。可追溯。版本控制。可审计。

### 每个Agent的有界上下文

反模式：Agent A传递一切给Agent B给Agent C（上下文窗口爆炸到100k+）。

修复：每个agent输出有界综合（最多2页）到下一个agent。在agent交接之间应用研究->计划->重置->实现。

### 构建你的第一个编排工作流

1. 选择最频繁的AI用例
2. 记录你目前手动执行的每个步骤
3. 设计循环：研究 -> 综合 -> 批评 -> 决策 -> 记录
4. 实现（简单场景用提示模板；复杂场景用API编排）
5. 在3个过去的例子上运行；与手动过程比较
6. 版本控制提示；培训2个队友；迭代

## AI验证（PoL探测）

### 5种探测类型

| 探测 | 核心问题 | 时间线 | AI特定用途 |
|------|----------|--------|-----------|
| **可行性检查** | 我们能构建这个吗？ | 1-2天 | GenAI提示链、API sniff测试、数据完整性扫描 |
| **任务聚焦测试** | 用户能无摩擦完成这个吗？ | 2-5天 | 测试AI生成的UI、聊天机器人流程、推荐质量 |
| **叙事原型** | 这能赢得认同吗？ | 1-3天 | 通过Loom/视频向利益相关者解释AI能力 |
| **合成数据模拟** | 我们能在没有生产风险的情况下建模吗？ | 2-4天 | 测试提示逻辑、模拟边缘情况、AI输出的蒙特卡罗 |
| **感觉编码探测** | 这能在真实用户接触中存活吗？ | 2-3天 | 用于工作流验证的Frankensoft堆栈（ChatGPT Canvas + Replit + Airtable） |

### 选择逻辑

从假设倒推：
1. 我在消除什么具体风险？
2. 到残酷真相的最便宜路径是什么？
3. 将方法匹配到假设，不是工具舒适度。

**黄金法则：** 使用告诉最残酷真相的最便宜原型。

### AI特定可行性检查

对于AI产品功能，可行性检查至关重要，因为AI能力不是显而易见的：
- **提示链测试：** 用100个真实例子运行你提出的提示。测量错误率。
- **API sniff测试：** 验证第三方AI集成返回预期格式、延迟、成本。
- **数据完整性扫描：** 检查你的数据是否支持AI功能（质量、数量、格式）。
- **处置协议：** 在记录发现后删除所有spike代码。Spike-and-delete，不是spike-and-ship。

### 成功标准模板

- **通过：** [定量阈值，例如 <5%错误率、80%+任务完成]
- **失败：** [可观察失败，例如 >18%错误、用户在流程中间放弃]
- **学习：** [无论通过/失败的特定洞察]

构建前写标准。"我们看到时会知道"不是成功标准。

### 故障排除常见AI产品问题

**幻觉（输出包含捏造的事实）：**
1. 测量：运行100+真实查询，分类错误（事实性、格式、推理、拒绝）
2. 减少上下文窗口 — 根据以上5个诊断问题剥离到最小必需token
3. 添加带源引用的检索 — 将答案扎根于特定文档，不是参数记忆
4. 添加输出验证 — 结构化字段的regex/规则检查，开放文本的LLM-as-judge
5. 设置置信阈值 — 如果模型置信度低，返回"我不知道"而不是猜测

**延迟（AI响应对UX太慢）：**
1. 分析管道 — 哪步慢？（检索、推理、后处理）
2. 减少输入token — 更小上下文 = 更快推理。应用持久化vs检索规则。
3. 使用流式处理 — 生成时显示部分结果
4. 缓存常见查询 — 如果30%查询相似，预计算答案
5. 考虑用更小模型处理简单任务 — 简单查询路由到快模型，难查询路由到强模型

**不一致（相同输入，不同输出）：**
1. 降低温度 — 事实任务用0.0-0.3，创造任务用0.5-0.7
2. 固定模型版本 — 生产中不要用"latest"
3. 结构化输出 — JSON schema或enum约束减少变化
4. 添加few-shot示例 — 2-3个输入/输出对锚定响应模式
5. 在固定测试集上评估 — 跨版本跟踪一致性分数

## 质量门

### AI产品反模式

**1. 提示和祈祷**
用未测试的提示发货AI功能。没有评估框架，没有错误率测量。修复：承诺构建前运行可行性检查（100+例子）。

**2. 规模化上下文填充**
将整个知识库粘贴到AI中。"更多token = 更好结果。"修复：应用5个诊断问题。准确性随着上下文增长显著下降（迷失在中间效应）。

**3. 无评估**
发货AI功能没有定量成功标准。"用户似乎喜欢它。"修复：构建前定义通过/失败阈值。测量错误率、任务完成、幻觉频率。

**4. 效率冒充策略**
"我们用AI写PRD快2倍 — 我们是AI形态的！"如果竞争对手通过雇2个人匹配，那是门槛。修复：问复制测试 — 复制需要组织重新设计吗？

**5. 工具迷恋**
"我们应该用 A 模型还是 B 模型？"工具辩论取代工作流重新设计。修复：工具不重要。工作流重要。

**6. 没有学习的速度**
构建更快而不验证更快。AI加速构建错误的东西。修复：压缩学习周期（PoL探测在几天内），而不仅仅是构建周期。

**7. 原型剧场**
构建抛光演示来给高管留下深刻印象，而不是用用户测试假设。修复：先与用户测试，在高管面前展示发现。叙事原型优先于生产抛光。

**8. 跳过重置**
在研究和实现之间从不清除上下文。上下文腐化毒害执行。修复：在计划综合后强制重置。只用高密度计划开始实现。

**9. 个人AI，不是团队AI**
"我是AI形态的，但我的团队不是。"无法规模化；你度假时工作流就死了。修复：编纂审查规范、证据标准、决策权威。团队转型 > 个人生产力。

**10. 测试多个变量**
一个探测同时测试工作流 + 定价 + UI。结果模糊。修复：一个探测，一个假设。三个假设 = 三个探测。

### 证伪协议

对于每个AI功能决策，完成：
> "如果我排除[上下文/功能/测试]，[具体失败]将在[具体场景]中发生。"

如果你不能完成这个句子，你不需要它。模糊失败（"AI可能不完全理解"）不是有效的。

### 最小可行AI产品检查清单

- [ ] 构建前写假设
- [ ] 运行可行性检查（100+例子，测量错误率）
- [ ] 定义上下文架构（持久化 vs 检索 vs 排除）
- [ ] 量化成功标准（通过/失败/学习阈值）
- [ ] 为探测设置处置日期（spike-and-delete）
- [ ] 分配上下文边界所有者
- [ ] AI输出视为草稿（人类审查协议）
- [ ] 测量学习周期（AI干预前 vs 后）
