# Feature Requirement Analysis

## 目标

把一个**已有功能**或**待实现需求**拆成 4 层结构化结论，全部基于代码事实，不臆造字段、不虚构接口。读者应当能在一遍阅读后：

1. 讲清楚这个功能的产品规则；
2. 在仓库里精准定位到任意一处实现；
3. 重建出它的数据 / 缓存模型；
4. 识别潜在的设计缺陷与改进点。

## 适用前提

- 仓库为典型 Go 多层结构：`app/api/route/*`（HTTP 入口）→ `service/*`（业务编排）→ `store/*`（持久化）→ `app/cron/*`（定时任务）→ `app/admin/*`（运营后台）。
- **优先用于复盘**仓库里已经存在的功能。如果需求尚未实现，则把"代码事实"替换为"接口契约 + 上下游依赖 + 字段假设"，并明确标注 `[未实现]`。
- 单次分析一个完整功能模块（不建议拆得太散，否则四层结构会被稀释）。

## 四层输出结构

每一层都有明确的"产出物"和"信息源"约束，必须按此执行：

### 一、产品需求

**产出物**：

- 业务定义（一句话讲清楚是什么 + 解决什么问题）。
- 角色与前置条件（谁能用、什么状态才能用）。
- 主流程状态机（**用表格**呈现：状态名 / 状态码 / 触发动作 / 关键校验）。
- 关键规则分支（奖励 / 配额 / 时间窗口 / 互斥关系）。
- 接口矩阵（C 端 / B 端 / 用户中心聚合，每张表里至少包含接口路径、用途、关键入参）。

**信息源**：

- `def/const.go`、`def/redis.go`、`def/coin.go` 等常量定义。
- HTTP handler 中的 `if` 条件、`serialize.Response` 错误码。
- 状态机的所有写入点（`Add` / `Save` / `UpdateExtra` 等）。

### 二、业务实现要点

**产出物**：

- 模块调用关系图（ASCII 框图即可：`api → service → store → db/redis`）。
- 关键业务约束清单（位置 / 约束 / 实现方式）。
- 定时任务清单（任务名 / 周期 / 职责 / 注册入口）。
- 幂等 / 锁 / 去重的具体 Key 与 TTL。
- 实现细节与坑点（不少于 3 条，**必须来自代码事实**，如 `Save()` 全字段覆盖、乐观锁条件、字段缺失等）。

**信息源**：

- `app/cron/service/*.go` 里的 `cronc.AddFunc`。
- `db.LoginRedis.Lock` / `SetExNx` 等调用。
- handler 里被忽略的边界条件（容易被忽略的 if、零值判断）。

### 三、存储设计

**产出物**：

- **MySQL 表结构**：给出 `CREATE TABLE`（如果源码注释里有，引用即可；没有则基于 `Add` / `Save` 反射推断并标注 `[推断]`）；列注释表格说明每列用途。
- **扩展字段**：如果有 JSON `extra` 列，给出其结构体定义与每个字段含义。
- **索引 / 约束缺口**：基于查询语句列出"应当有但没有"的索引或唯一约束。
- **Redis Key 设计**：Key 模式 / 类型 / 作用 / TTL 表。
- **关联表**：列出语义相关但不在本模块的表与关系（外键、资金流水、上游实体）。
- **状态流转 + 字段变化矩阵**：每一步流转触发哪些字段变化。

**信息源**：

- `store/*/xxx.go` 顶部的建表注释。
- `helper.GetStructTag` / `Add` / `Save` 的 SQL 反射。
- 所有 `db.MainDB` / `db.ReadOnlyMainDB` 查询语句。
- 所有 Redis Key 的常量定义。

### 四、风险与改造

**产出物**（每条都基于代码事实，不发散）：

- 状态机漏洞（如：定义但未写入的常量、被过滤但无来源的状态）。
- 业务与实现的脱节（如：仅展示未入账的计算函数）。
- 并发 / 原子性缺口（如：缺少唯一约束、锁 TTL 过短）。
- 性能隐患（如：内存过滤 + 分页、全表扫）。
- 数据一致性（如：离婚 / 注销后子表状态未联动）。

每条都要写明：**位置 / 现象 / 建议（可写可不写，但必须可定位）**。

## 通用工作流

每次接到"分析 XX 需求 / 功能"的任务，按以下步骤执行：

```
1. 入口定位
   - Grep 关键词（功能中文名 + 英文名 + 业务术语），先找全部命中文件。
   - 列出 openspec / docs 里是否有相关规约文档，优先参考。

2. 入口层 → 业务层 → 存储层 三段式阅读
   - 先读 HTTP handler / 路由注册，理解外部接口形状。
   - 再读 service 层，理解业务编排。
   - 最后读 store 层，理解持久化模型。

3. 常量与定时任务补全
   - def/* 找状态码、Key、奖励金额、PropId、CoinChangeType 等。
   - app/cron/service/* 找定时任务。
   - app/admin/route/* 找运营后台能力。

4. 状态机重建
   - 列出所有 state 写入点（包含 cron / admin / handler），画出完整流转图。
   - 对每个状态标注：触发条件、终态性、是否可被回滚。

5. 写出四层结论
   - 按"产品需求 / 业务实现 / 存储设计 / 风险与改造"顺序输出。
   - 每个结论都必须可被某段代码引用佐证。
```

## 表达约定

- 中文输出，使用 markdown 表格、ASCII 框图、列表。
- 关键代码引用使用 `文件路径:行号范围` 形式（如 `store/insurance/insurance.go:67-80`）。
- **不要编造字段、接口、参数**——如果源码没找到就标 `[未在源码中找到]`。
- 状态码、Key 名、PropId 等常量必须与源码一致（含大小写、下划线）。
- 时间单位：源码中是秒就写秒、是毫秒就写毫秒，必要时换算。

## 反模式（不要这么做）

- 不要把分析写成"流水账"——按文件逐个解释。应当按"主题"组织。
- 不要混入"未来规划 / 优化建议"到主结论里，全部放在第四层。
- 不要使用 emoji（除非用户明确要求）。
- 不要在没读到代码时给出"应当是 XX"——用 `[推断]` 或 `[未在源码中找到]` 标注。
- 不要遗漏定时任务、运营后台——这是 wespy 这类仓库最容易被漏掉的能力。

## 输出长度指引

- 单个功能的完整分析通常在 **300~600 行 markdown**。
- 如果超过 800 行，说明主题过大，应当拆分为多个子功能分别分析。
- 如果不足 200 行，说明挖得不够深，回到第二、三层继续挖。
