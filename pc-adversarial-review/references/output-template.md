# 输出模板：审查报告 + 修订版

本文件定义最终交付物的**格式规范**。每次审查结束必须按此输出，禁止自由发挥、禁止缺项。

---

## 一、三级模式与输出裁剪

输出量随模式动态裁剪，**核心板块三模式全保留**：

| 板块 | 极速 | 标准 | 深度 |
|---|---|---|---|
| 审查对象摘要 | ✅ | ✅ | ✅ |
| 需求落实速览表 | ✅ | ✅ | ✅ |
| 链路对齐清单 | ✅（仅主链路） | ✅ | ✅ 详尽 |
| 总体结论 | ✅ | ✅ | ✅ |
| 问题分级清单 | 仅 P0/P1，精简 | 全量（含 P2） | 全量 + 详尽依据 |
| 参与专家 | 简表 | 含选配理由 | 含选配理由 + 预判质疑 |
| 分歧与共识 | 合并进总体结论 | ✅ | ✅ 详尽 |
| 质问官验收 | 合并进速览表 | ✅ | ✅ 逐条详尽 |
| 保留意见 | 仅 P0/P1 涉及 | ✅ | ✅ |
| 自动修订版 | ❌ | ❌ | ✅ |

**合并原则**：低级别模式下，次要板块合并进主要板块，不重复输出。

---

## 二、审查报告结构（固定顺序）

```
【审查对象摘要】
（大白话复述：这个方案/代码/文档是干什么的、谁要用、要达到什么目的）

【工具扫描摘要】（代码/技术类且工具可用时显示，其他类型或无工具时跳过）
- 使用工具：
  代码质量：ESLint ✅  Ruff ❌（非 Python）
  架构分析：GitNexus ✅（已索引，XX 个仓库）  / ❌（未索引/不可用）
  安全扫描：Snyk ❌（未接入）
  数据/接口：DB Schema ❌（未接入）  OpenAPI ❌（未接入）
- 代码质量发现：X 个错误，X 个警告，其中 X 个可自动修复
- 架构分析发现（GitNexus 可用时）：
  - 变更影响 X 个模块，最深调用链 X 层
  - 关键发现：X 个高风险影响点
  - 污点分析：已执行 / 未执行（非深度模式）
- 说明：详细扫描结果已作为专家审查依据纳入问题清单

【链路对齐清单】（核心：让用户一眼看到整条链路哪里对不齐）
先放「链路图」：起点 → 节点1 → 节点2 → 终点（每个节点一句话说明输入/输出、衔接关系）
再放「链路对齐表」：
| 链路环节 | 该环节的作用（大白话） | 状态 | 对不齐的地方（如有） |
（状态四选一：✅ 通 / ❌ 断 / ❌ 错位 / 🔍 不确定；填写规范见 chain-review.md 第六节）

【需求落实速览表】（放在最显眼处，小白第一眼答案）
（逐条列出用户要的功能点：✅ 已实现 / ⚠️ 只做了一部分 / ❌ 没做 / 🔍 不确定
  用用户自己的话描述，禁止出现用户没提过的功能；格式见下）

【参与专家】
（名单 + 各自角色 + 选配理由）

【总体结论】
- 通过 / 有条件通过 / 不通过
- 一句话说明依据（大白话）
- 极速模式：分歧与共识、质问官结论合并在此简述

【问题分级清单】
P0（致命）：逐条列出
P1（严重）：逐条列出
P2（建议）：逐条列出（极速模式不列）
（每条按下方「问题条目格式」输出；修改建议附在条目内）

【分歧与共识】（标准/深度模式）
- 共识：多位专家共同指出的问题（优先处理）
- 分歧：对立观点 + 主持人裁定结果

【保留意见】
（某专家仍持异议的，如实列出）

【质问官核对】（标准/深度模式）
（逐条核对结果，格式见下；极速模式已在速览表体现）
```

### 需求落实速览表格式

```
| 你要的功能 | 落实情况 | 说明（大白话） |
|---|---|---|
| 功能 1（用用户原话描述） | ✅ 已实现 | 在 xx 里做到了，你点 xx 就能看到 |
| 功能 2 | ⚠️ 只做了一部分 | 能 xx 但不能 xx，还差一步 |
| 功能 3 | ❌ 没做 | 目前完全没有，需要补做 |
| 功能 4 | 🔍 不确定 | 现有信息看不出来，需要补充 xx 才能确认 |
```

**硬要求**：
1. 功能点用**用户原话或最直白转述**，禁止用技术术语
2. 与「质问官验收清单」结论必须一致
3. 放在报告最显眼处（摘要之后），让小白第一眼看到答案
4. 用户输入里没有明确功能清单时，先确认「你想要的到底是哪几个功能」

## 三、问题条目格式（每条必含）

```
【问题】问题是什么（大白话，一句话）
【严重度】P0 / P1 / P2
【依据】为什么说是问题（引用输入中的实际内容）
【原因分析】为什么会这样（大白话）
【链路影响】在链路的哪个环节、上下游、牵动面（P0/P1 必填，P2 可简写）
【修改建议】具体怎么改（可执行，大白话）
【大白话版】向不懂行的人解释（P0/P1 必填，P2 可省）
```

**按严重度精简**：
- P0/P1：全字段输出（含大白话版）
- P2：可精简为「问题 + 严重度 + 修改建议」

---

## 四、质问官验收清单

```
| 问题编号 | 原问题摘要 | 修订方式 | 验收结果 | 验证依据 |
|---|---|---|---|---|
| P0-1 | ... | ... | 已通过 / 未通过 / 不确定 | ... |

验收结论：全部通过 → 可交付；存在未通过/不确定 → 附未验收清单交付
```

**验收两件事**：
1. 修订版是否符合用户原始需求（需求符合度）
2. 每个「已修复」是否有验证依据（修复真实性）

信息不足无法确认 → 标「不确定」+ 说明缺什么。

## 五、自动修订版规范（仅深度模式或用户要求时生成）

```
【修订版完整内容】
（在原方案/代码/文档基础上，直接给出修改后的完整版本）

【变更对比表】
| 位置 | 原内容 | 修订后 | 为什么改 |
|---|---|---|---|
| ... | ... | ... | ... |

【修订说明】
- 一共改了 X 处（P0: X 处、P1: X 处、P2: X 处）
- 每处修订与原始问题的对应关系（可追溯）
- 修改后是否有已知遗留问题或新风险
```

**四条硬约束**：
1. **逐条对应**：每个原问题都有对应处理，禁止遗漏
2. **不编造**：基于输入真实内容修订，禁止虚构不存在的函数/API/事实
3. **可追溯**：每处改动都能说明「改了什么、为什么改」
4. **查回归**：检查修订是否引入新问题、破坏原有逻辑

代码类额外要求：修复前后给代码对比（diff 或前后片段）。

---

## 六、大白话原则

1. 默认通俗模式：全文大白话，非必要不出现技术名词、黑话、缩写
2. 必须用术语时，首次出现加括号解释（例：耦合（各模块互相纠缠，改一处坏一片））
3. 用户说「可以用术语」时关闭通俗模式
4. 输出前自检：「给完全不懂行的朋友看，他能看懂吗？」

---

## 七、严重度分级

| 级别 | 含义 | 判定标准 | 处理要求 |
|---|---|---|---|
| P0 | 致命 | 不改会出事：安全事故 / 法律风险 / 商业不成立 / 核心目标无法达成 | 必须修复 |
| P1 | 严重 | 明显影响目标达成、用户体验、长期可维护性 | 应修复，给具体方案 |
| P2 | 建议 | 优化项，不影响成败 | 可选修复，给建议即可 |

---

## 八、输出语言

- 默认使用用户输入的语言（中文输入 → 中文报告）
- 代码类审查中，代码注释/术语可用技术语言，但解释必须大白话
- 所有「大白话版」字段与用户语言一致

---

## 九、降级报告（上下文不足时）

```
【初步审查声明】
（本报告基于现有信息完成，属于初步结论，受信息完整度限制）

【信息缺口清单】
- 缺 XX：影响「对 XX 的判断」——补充后即可确认
- 缺 XX：影响「对 XX 的判断」——补充后即可确认

【初步审查内容】
（按正常报告结构输出，但缺信息处一律标「🔍 不确定」）

【续审指引】
（补充上述信息后，可以接着缺口继续深挖，无需从头再来）
```

**硬要求**：
1. 必须显式声明是初步结论，禁止伪装成完整报告
2. 信息缺口必须逐条说明「缺什么 → 影响什么 → 补了能得到什么」
3. 缺信息处一律标「🔍 不确定」，绝不编造
4. 续审时基于原审查结果继续，禁止推倒重来

## 十、MCP 结构化输出（JSON 格式）

当通过 MCP 工具调用、或用户明确要求结构化输出时，除了正常的大白话报告外，还需输出以下 JSON 格式的结构化数据（供程序消费）。

### 输出结构

```json
{
  "summary": {
    "review_type": "plan-decision | code-tech | document-content | mixed",
    "mode": "quick | standard | deep",
    "experts": ["专家1", "专家2", "..."],
    "overall_conclusion": "pass | conditional-pass | fail",
    "conclusion_basis": "一句话结论（大白话）"
  },
  "requirements_checklist": [
    {
      "requirement": "用户需求描述",
      "status": "implemented | partial | missing | uncertain",
      "explanation": "大白话说明"
    }
  ],
  "chain_alignment": [
    {
      "node": "链路环节",
      "role": "该环节作用（大白话）",
      "status": "ok | broken | misaligned | uncertain",
      "misalignment": "对不齐的地方（无则 null）",
      "related_issue_id": "对应问题ID（无则 null）"

  ],
  "issues": [
    {
      "id": "P0-1",
      "severity": "P0 | P1 | P2",
      "problem": "问题是什么",

    "consensus_points": ["共识问题"],
    "divergence_points": [
      {
        "issue": "分歧点",

        "verdict": "主持人裁定"
      }
    ],
    "dissenting_opinions": ["保留意见"]
  },
  "verification": {
    "officer_check": [
      {
        "issue_id": "P0-1",
        "issue_summary": "问题摘要",

      {
        "position": "改动位置",
        "original": "原内容",

  },

    {
      "missing_info": "缺什么信息",

    }

```

### 说明

- 结构化输出与大白话报告内容必须一致，不能出现矛盾
- 极速/标准模式下，`revised_content` 字段可为 `null`
- 没有信息缺口时，`context_gaps` 为空数组
- MCP 调用时，默认返回此 JSON 结构；正常对话时，输出大白话报告
- 完整的输入/输出契约定义见 SKILL.md 第十六节
