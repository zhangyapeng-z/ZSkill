# MCP 工具预检配置

本文件定义了不同审查类型对应的 MCP 工具调用清单和规则。第 4 步「工具预检」时按本文件执行。

---

## 一、工具可用性检测

工具预检开始前，先检测对应 MCP 工具是否可用。检测方式：尝试调用工具的一个轻量操作（如查询配置、版本信息、列表），如果报错则标记为不可用，跳过该工具，不阻塞审查流程。

**GitNexus 可用性检测方式**：调用 `list_repos` 查看是否有已索引的仓库。如果返回空列表或报错，标记为不可用，跳过 GitNexus 扫描。

**可用工具列表**（按 MCP 服务器分组）：

| MCP 服务器 | 工具名 | 用途 | 适用类型 |
|-----------|--------|------|---------|
| **ESLint** | `eslint_lint_file` | 单文件 JS/TS 代码检查 | 代码/技术（JS/TS） |
| ESLint | `eslint_lint_directory` | 目录级代码检查 | 代码/技术（JS/TS） |
| ESLint | `eslint_fix_file` | 自动修复可修复问题 | 代码/技术（JS/TS） |
| ESLint | `eslint_get_config` | 查询文件的 ESLint 配置（可用性检测用） | 代码/技术（JS/TS） |
| **Ruff** | `ruff_check` | Python 代码 lint 检查 | 代码/技术（Python） |
| Ruff | `ruff_format_check` | Python 格式检查 | 代码/技术（Python） |
| Ruff | `ruff_fix` | 自动修复 lint 问题 | 代码/技术（Python） |
| **GitNexus** | `list_repos` | 列出已索引的仓库（可用性检测用） | 代码/技术（所有语言） |
| GitNexus | `query` | 混合检索（BM25 + 语义 + RRF，返回执行流/调用链） | 代码/技术（功能定位、链路还原） |
| GitNexus | `context` | 符号 360° 全景视图（调用者、被调用者、所属集群） | 代码/技术（架构、功能、安全） |
| GitNexus | `impact` | 爆炸半径/影响范围分析 | 代码/技术（架构、可维护性） |
| GitNexus | `detect_changes` | git diff 影响映射（变更 → 符号 → 执行流） | 代码/技术（变更审查） |
| GitNexus | `route_map` | API 路由全图 | 代码/技术（架构、接口） |
| GitNexus | `api_impact` | API 变更影响报告 | 代码/技术（接口） |
| GitNexus | `shape_check` | API 响应形态与消费者字段访问核对 | 代码/技术（接口） |
| GitNexus | `cypher` | 原始 Cypher 图查询（自定义依赖/调用路径分析） | 代码/技术（高级自定义、安全路径分析） |
| **Snyk（可选）** | `snyk_code_scan` | 代码安全扫描（SAST） | 代码/技术（安全） |
| Snyk（可选） | `snyk_sca_scan` | 依赖漏洞扫描（SCA） | 代码/技术（依赖） |
| Snyk（可选） | `snyk_secret_scan` | 密钥检测 | 代码/技术（安全） |
| **dev-toolkit DB** | `db_list_connections` | 列出已配置的数据库连接 | 架构/接口类 |
| dev-toolkit DB | `db_schema` | 获取数据库表结构 | 架构/接口类 |
| dev-toolkit DB | `db_query` | 执行 SQL 查询 | 架构/接口类 |
| **OpenAPI（可选）** | `list-api-endpoints` | 列出所有 API 端点 | 架构/接口类 |
| OpenAPI（可选） | `get-api-endpoint-schema` | 获取端点详细 Schema | 架构/接口类 |

> **可选工具口径**：Snyk / OpenAPI 仅在环境已接入对应 MCP 时使用；未接入时直接跳过，安全相关项在报告中标记「未自动扫描，人工复核」。

## 二、三级扫描机制

> **前置动作：链路还原**（第 4 步强制，先于三级扫描）。用 GitNexus `query`/`context`/`impact` 还原审查对象的完整链路（调用链/数据流/功能流），产出「链路图」作为所有专家的共同上下文。GitNexus 不可用时人工梳理。方法论见 `chain-review.md`。

代码/技术类审查的工具预检分为三级，逐级升级：

```
第一级：单文件质量扫描（ESLint / Ruff）
    ↓ （只要是代码类就执行）
第二级：架构影响扫描（GitNexus）
    ↓ （仓库已索引 + 非单文件小片段时执行）
第三级：深度安全扫描（GitNexus 深度路径分析 + 人工审查）
    ↓ （深度模式 + 涉及安全敏感代码时执行）
```

**升级规则**：
- 只要是代码/技术类审查，第一级必做
- 第二级触发条件：GitNexus 可用 + 审查内容涉及项目级代码（不是只有几行代码片段）
- 第三级触发条件：深度模式 + 审查内容涉及安全敏感场景（认证、权限、数据处理、外部输入等）

## 三、各类型工具预检清单

### 3.1 代码/技术类（JavaScript / TypeScript）

**触发条件**：审查类型=代码技术，且代码文件为 .js / .jsx / .ts / .tsx

| 级别 | 顺序 | 工具 | 调用时机 | 给谁用 |
|------|------|------|---------|--------|
| 一级 | 1 | `eslint_lint_file` 或 `eslint_lint_directory` | 工具预检阶段 | 安全审计员、可维护性审查官 |
| 二级 | 2 | GitNexus `detect_changes`（有 diff 时）或 `impact`（有目标符号时）或 `context`（核心符号） | 工具预检阶段 | 架构审查官、功能逻辑审查官、可维护性审查官 |
| 二级 | 3 | GitNexus `query`（搜索关键功能） | 工具预检阶段 | 功能逻辑审查官 |
| 三级 | 4 | GitNexus `cypher` / `query`（安全场景：自定义依赖/调用路径分析，追踪外部输入传播） | 深度模式 + 安全相关 | 安全审计员 |
| 可选 | 5 | `snyk_code_scan`（已接入 Snyk 时用；未接入则安全项标注「未自动扫描，人工复核」） | 工具预检阶段 | 安全审计员 |
| 可选 | 6 | `snyk_sca_scan`（已接入 Snyk 时用） | 工具预检阶段 | 依赖风险审查官 |

**调用规则**：
- 如果用户提供了单个文件路径，用 `eslint_lint_file`
- 如果用户提供了目录或项目路径，用 `eslint_lint_directory`
- GitNexus 调用逻辑：
  - 用户给了 git diff / PR 链接 → 优先用 `detect_changes`
  - 用户给了具体的函数/类名 → 用 `impact` + `context`
  - 用户描述了功能需求 → 用 `query` 搜索相关执行流
  - 仓库未索引或工具不可用 → 跳过，报告中标注
- Snyk 属可选增强：仅环境已接入 Snyk MCP 时调用其结果；未接入时跳过，安全相关项在报告中标记「未自动扫描，人工复核」
- 扫描结果注入对应专家的人设，专家审查时必须引用扫描结果

**GitNexus 结果注入格式**：
```
【工具扫描结果 - GitNexus 架构分析】
- 已索引仓库：XXX（状态：已索引 / 未索引）
- 影响范围分析：
  - 变更涉及 X 个符号，影响 X 个上游模块
  - 核心功能集群：XXX、XXX
  - 调用链深度：最深 X 层
- 关键发现摘要：
  1. [发现点] - 影响模块：XXX、XXX - 风险等级：中/高
  2. ...
- 深度安全分析（仅三级扫描时）：
  - 高风险调用路径 X 条（外部输入 → 关键操作）
  - 关键路径：入口 → ... → 敏感操作
```

### 3.2 代码/技术类（Python）

**触发条件**：审查类型=代码技术，且代码文件为 .py

| 级别 | 顺序 | 工具 | 调用时机 | 给谁用 |
|------|------|------|---------|--------|
| 一级 | 1 | `ruff_check` | 工具预检阶段 | 安全审计员、可维护性审查官 |
| 一级 | 2 | `ruff_format_check` | 工具预检阶段 | 可维护性审查官 |
| 二级 | 3 | GitNexus `impact` / `context` / `detect_changes` | 仓库已索引时 | 架构审查官、功能逻辑审查官 |
| 三级 | 4 | GitNexus `cypher` / `query`（安全场景：自定义依赖/调用路径分析） | 深度模式 + 安全相关 | 安全审计员 |
| 可选 | 5 | `snyk_code_scan`（已接入 Snyk 时用；未接入则安全项标注「未自动扫描，人工复核」） | 工具预检阶段 | 安全审计员 |

**调用规则**：
- 路径可以是单个文件或目录
- GitNexus 规则同 3.1
- Snyk 未接入时跳过，安全相关项标注「未自动扫描，人工复核」
- 扫描结果注入对应专家人设

### 3.3 架构/接口类

**触发条件**：审查内容涉及数据库设计、API 接口设计、系统架构

| 级别 | 顺序 | 工具 | 调用时机 | 给谁用 |
|------|------|------|---------|--------|
| 二级 | 1 | GitNexus `route_map` / `impact` / `context` | 仓库已索引时 | 架构审查官、功能逻辑审查官 |
| 二级 | 2 | GitNexus `shape_check`（接口响应形态核对） | 仓库已索引且涉及 API 时 | 架构审查官、功能逻辑审查官 |
| 可选 | 3 | dev-toolkit DB 工具：`db_list_connections` → `db_schema` / `db_query` | 工具预检阶段（需数据库连接） | 架构审查官、功能逻辑审查官 |
| 可选 | 4 | OpenAPI 工具（已接入时） | 工具预检阶段 | 架构审查官、功能逻辑审查官 |

**调用规则**：
- GitNexus 是架构审查的主力工具（只要索引了就优先用）
- dev-toolkit 数据库工具先用 `db_list_connections` 确认连接 ID，再用 `db_schema` / `db_query`；未配置数据库连接时跳过
- OpenAPI 未接入时跳过
- Schema 信息用于辅助架构审查官判断设计合理性

### 3.4 方案/决策类、文档/内容类

**不执行工具预检**。这些类型的审查依赖专家的逻辑判断，不需要工具扫描。

## 四、工具调用优先级与降级策略

### 4.1 优先级

1. **代码质量工具优先**（ESLint / Ruff）：最稳定、最容易配置、结果最具体
2. **架构分析工具其次**（GitNexus）：只要索引了就有高价值，覆盖架构、功能、安全多维度
3. **安全扫描工具（Snyk，可选）**：仅在环境已接入时使用，未接入时安全项人工复核并在报告标注
4. **数据/接口探查工具最后**（dev-toolkit DB / OpenAPI）：数据库工具开箱即用（需已配置连接），OpenAPI 需额外接入

### 4.2 降级策略

| 场景 | 处理方式 |
|------|---------|
| 工具完全不可用 | 跳过工具预检，报告开头标注「本次未使用工具扫描，结论基于人工审查」 |
| 部分工具可用 | 用可用的工具，不可用的跳过，报告中说明哪些工具未启用 |
| 工具调用超时 | 跳过该工具，继续审查，标注「工具调用超时，未使用该工具结果」 |
| 扫描结果为空 | 说明代码/配置没有发现工具可检测的问题，专家仍需进行人工审查 |
| GitNexus 仓库未索引 | 跳过 GitNexus 扫描，报告中标注「未使用架构级扫描（仓库未索引）」 |
| GitNexus 索引过旧 | 仍可使用，但标注「索引可能存在滞后，结论仅供参考」 |

## 五、专家与工具的对应关系

| 专家角色 | 使用哪些工具的结果 | 怎么用 |
|---------|-------------------|--------|
| **功能逻辑审查官** | GitNexus `query` / `context` | 快速定位功能全链路，验证流程完整性，确认功能边界 |
| **安全审计员** | ESLint（安全规则）、Snyk Code/SCA（已接入时）、**GitNexus `query` / `cypher`** | 引用扫描结果作为依据 + GitNexus 追踪攻击路径和外部输入传播，人工分析实际影响；Snyk 未接入时安全项人工复核并标注 |
| **架构审查官** | dev-toolkit DB（`db_schema`/`db_query`）、OpenAPI（已接入时）、**GitNexus `impact` / `context` / `route_map` / `cypher`** | 用真实依赖图验证架构设计、量化耦合度、识别循环依赖 |
| **性能工程师** | ESLint（复杂度规则）、**GitNexus `context` / `query` / `cypher`** | 分析调用深度、识别重复计算、发现架构级性能瓶颈 |
| **可维护性审查官** | ESLint / Ruff（风格、复杂度）、**GitNexus `impact` / `context`** | 引用 lint 问题 + GitNexus 量化变更成本和模块耦合度 |
| **依赖风险审查官** | Snyk SCA（已接入时）、**GitNexus `impact`** | 用漏洞数据 + 影响范围评估依赖风险的实际严重度 |
| **边界情况猎手** | GitNexus `query` / `context`（辅助） | 找异常处理链路、验证边界输入的传播路径 |

**GitNexus 工具在专家审查中的地位**：
- 架构审查官、安全审计员：GitNexus 是**核心工具**，大幅提升审查深度
- 功能逻辑审查官、可维护性审查官：GitNexus 是**效率工具**，节省定位时间
- 性能工程师、边界情况猎手：GitNexus 是**辅助工具**，提供额外视角
- `query` / `impact` / `context` 是**链路还原的标配工具**（第 4 步链路还原时调用），产出链路图后注入所有专家，不限于架构审查官

## 六、工具结果使用规范

### 必须遵守

1. **工具结果是依据，不是结论**：专家必须结合人工分析，不能只罗列工具输出
2. **必须标注来源**：引用工具结果时注明「ESLint 检测到」「Snyk 扫描发现」「GitNexus 影响分析显示」
3. **必须有修改建议**：工具报告的问题，专家也要给出修改方案，不能只甩工具输出
4. **工具遗漏的问题也要指出**：专家不能因为工具没扫出来就忽略明显的问题
5. **GitNexus 结果必须人工验证**：知识图谱可能有解析误差，关键结论需要对照源代码确认

### 禁止行为

1. 禁止把工具扫描结果直接当作专家意见（那是工具输出，不是专家审查）
2. 禁止夸大工具结果的严重度（工具说 warning 就按 warning 来，不能升成 P0）
3. 禁止用工具结果代替人工逻辑分析
4. 禁止因为工具没扫出问题就说「没问题」
5. 禁止把 GitNexus 的图查询结果当绝对真理（可能有解析遗漏，特别是动态语言）

## 七、输出模板中的工具扫描结果展示

在审查报告的「审查对象摘要」之后，增加「工具扫描摘要」板块（仅代码/技术类且工具可用时）：

```
【工具扫描摘要】
- 使用工具：
  代码质量：ESLint ✅  Ruff ❌（非 Python）
  架构分析：GitNexus ✅（已索引，XX 个仓库）
  安全扫描：Snyk ❌（未接入，安全项未自动扫描，已人工复核）
  数据/接口：dev-toolkit DB ❌（未配置连接）  OpenAPI ❌（未接入）
- ESLint 发现：X 个错误，X 个警告，其中 X 个可自动修复
- GitNexus 架构分析：
  - 变更影响 X 个模块，最深调用链 X 层
  - 关键发现：X 个高风险影响点
  - 深度安全分析：已执行 / 未执行（非深度模式）
- 详细扫描结果已纳入专家审查依据
```
